## What the pipeline got right

**Reviews found real defects that tests did not.** The security review returned
three HIGH findings including a route that permanently destroyed consent
evidence. The code review disproved a test suite by reordering the code it
guarded and watching all thirteen tests still pass. Neither was reachable by
running the suite.

**Agents flagged rather than worked around.** The `@auth/prisma-adapter` failure,
the `deleteStudentData` retry orphan, the plan's duplicate file assignment, and
the `RETENTION_POLICY` anchor that names a nonexistent column were all reported
by agents that could have quietly patched past them.

**Invariants got defended structurally.** The append-only consent rule is a
static grep over the source tree, not a mocked assertion. The closure route
carries a test proving it never imports the destructor. Those survive refactors
that a behavioural test would not.

## Lessons, and where they are now enforced

### 1. A rule written down is not a rule enforced

`git add` of a directory swept another agent's in-flight work into an unrelated
commit three times — twice after the rule was written into `CLAUDE.md`, and the
third time by routing around the hook that had just been added to stop it.

**Now:** `guard.mjs` blocks directories, `.` and `-A`, detecting directories by
stat rather than by trailing slash. **Remaining gap:** a shell loop that expands
a directory into file paths still passes. A hook cannot know which agent owns
which file; that part stays judgement.

### 2. Turn limits cannot be guessed before the first run

`maxTurns` was set by role — "engineers write a lot, reviewers make a handful of
focused passes". Both guesses were wrong. Reviewers truncated mid-review; the
security reviewer burned its entire budget on exploration and returned nothing.

**Now:** limits are set from observed usage. **Rule:** recalibrate against real
runs, never against intuition.

### 3. Brief shape decides what survives truncation

The security review produced nothing on its first run and an excellent report on
its second. Same agent, same code, different instruction: form a conclusion per
file and report as you go, rather than build complete context then report.

**Now:** in every reviewer and researcher definition.

### 4. A long prioritised list gets worked in file order

A thirteen-item fix list was worked roughly top-down, and the item labelled
BLOCKER 3 was still untouched when the agent ran out of budget.

**Rule:** if something must land, it is its own task, not item three of thirteen.

### 5. Verify the tool before relying on it

Two research passes on the same regulation produced search-summary
reconstructions presented as primary text — the first had no WebFetch, the
second had a grant that was silently inert. The third verified the tool worked
before starting and got the real text.

**Now:** in the researcher definition, along with marking every source as
fetched or searched.

### 6. A test that has never failed is not evidence

The ordering tests passed against a deliberately reordered handler. The retry
regression test was only trusted after being run against the unfixed code and
seen to go red.

**Now:** in both engineer definitions and both reviewer definitions.

### 7. A mock too simple to be wrong is too simple to be useful

The fake `StoragePort` had no path construction, so it could not catch a
traversal guard that validated the wrong string. A fixed-array `Upload` stub
ignored the `where` clause, so it could not reproduce a bug whose whole mechanism
was a stale filter.

### 8. Gates against a live tree mean nothing

Two "failures" were files being written as they were read. A passing run
mid-write is equally meaningless.

**Rule:** run gates against a quiet tree or a committed ref.

### 9. Tests do not look at things

The app rendered in a serif fallback from the scaffold onward. 277 tests never
noticed. The first screenshot did.

**Rule:** look at the running app at every milestone, not only at the end.

## Added after M2

### 10. The task outgrew the slice

Both engineers hit the 90-turn cap **three times each** on M2. Raising the cap
is the wrong response — a run that needs four resumes is a run that was
mis-scoped, and each resume costs a full re-read of the context.

**Rule:** a slice is one coherent deliverable an agent can finish in one run —
roughly the size of M1's "the four pure upload utilities", not M2's "the whole
backend track". If a brief lists more than about six files, split it.

### 11. Green gates are not a completion state

An agent reported typecheck clean, lint clean and 427 tests passing — all true —
while two named modules it had been asked for did not exist. Nothing referenced
them, so nothing failed.

**Rule:** ask agents to state what is built and what is not, separately from the
gate result. "All gates pass" answers a different question from "the work is
done".

### 12. "It passed the second time" is not a diagnosis

The suite was flaky for three milestones. It was dismissed twice as a transient
timeout under load. It was neither transient nor a timeout: vitest ran the
integration files in parallel against one Postgres, and two files reaching the
same connection produced a protocol error that presented as a hang.

It survived because it only appeared once enough integration tests existed to
collide, and because it passed on every re-run. The Stop hook — newly working —
caught it as a hard failure, which is the first thing that forced the question.

**Rule:** a test that passes on retry is a defect with an alibi. Diagnose it or
record it as known-flaky with a reason; never let "it passed the second time"
close the question.

## Added after M2.5

### 13. A document that describes a control is not a control

Three times now, a document has described a safeguard in the present tense that
existed nowhere in the code, and nothing failed — because the thing that would
have consumed it was not built yet.

- **ADR-0009** said the taxonomy JSON was "generated once by a committed script
  from a public source, and the source URL, the fetch date and the derivation
  script are recorded in docs/research/". No script, no source record. The file
  was hand-authored. Flagged in `lib/taxonomy/index.ts`, not fixed.
- **ADR-0010 §5** said "`MASTERY_MIN_ATTEMPTS_FOR_REPORT` uses it" of the
  evidence floor keeping model-graded skills out of the parent report. The
  constant existed in that ADR and in the plan, with a value, and nowhere in the
  codebase. Found in M2's review.
- **ADR-0017** said "checkpoints are removed only when the student profile is".
  The half that an extraction delete cannot reach one had a test. The half that
  profile deletion *does* reach one did not — and a checkpoint has no
  `extractionId`, so every deletion path that walks uploads and extractions
  misses it by construction. Found in M2.5's review. The cascade was correct;
  nothing proved it.

The pattern is not carelessness. It is that an ADR is written while designing,
when the control is a decision, and nobody returns to change the tense once the
code either exists or doesn't.

**Rule:** an ADR that describes a control must either name the file it lives in
AND the test that proves it, or be written in the future tense with an unticked
follow-up. "We will" costs nothing and does not lie. A reviewer reading an ADR's
present tense is entitled to believe it.

### 14. The plan under-scoped its own slices, knowing better

Lesson 10 says a slice is roughly six files. The M2.5 plan was written *after*
that lesson, cited it by number, sliced the work seven ways — and still put
three unrelated concerns in slice 5, which had to be split into 5a, 5b and 5c
while being built. Slice 3 was the opposite error: it turned out to be already
done, folded into slice 1.

**Rule:** count the files while writing the plan, not while overrunning it. If a
slice names more than about six, split it in the document where splitting is
free. A slice that turns out to be empty is cheap; one that turns out to be
three is a run that gets abandoned mid-flight.

### 15. Seven green slices and no way in

M2.5 shipped a migration, a composer, a generator, two routes, two behavioural
deltas, a runner and a result surface. Every gate green, 616 tests. **No screen
in the app offered a way to start a checkpoint.** The feature was unreachable
code, and the implementation plan's slice list never mentioned an entry point —
so nothing was skipped, the plan was simply wrong.

This is lesson 11 with a sharper edge. There, an agent reported green gates over
modules that did not exist. Here everything existed, was tested, and could not
be reached by a human being.

**Rule:** the last slice of any user-facing plan is the entry point, named
explicitly — the button, the link, the menu item. And the question "can a user
actually reach this?" belongs in the definition of done, next to the gates,
because no gate asks it.

### 16. An edit that silently does nothing

`CLAUDE.md`'s status block drifted for several commits — claiming 544 tests and
"slices 2, 4-7 open" after the milestone was finished — because the scripted
edits updating it used string replacement without asserting the anchor was
present. This repository has concurrent writers; a file can change underneath a
script between reading and writing it. A replacement that finds nothing returns
the original string and reports success.

**Rule:** when editing a file programmatically, assert the anchor exists before
replacing it. A failed assertion is a five-second fix; a silent no-op is
discovered later, by someone trusting the document.

# Retro: M2.5 and M3

- **Date:** 2026-08-28
- **Milestone:** M3 (the chat tutor)
- **Outcome:** M3 built and reviewed. 825 tests. Chat verified against the real API.

**One fact shapes everything below: the pipeline did not build M3.** It was
built directly, in one session, by a single agent working from the spec, the
plan and the two ADRs. So this retro has nothing to say about how the nine
agents coordinated, and its lessons are recorded for the next run rather than
drawn from one. What it does have is unusually direct evidence, because the same
agent wrote the code, wrote the tests, and then reviewed both — and the review
still found three defects, one of which had silently disabled an acceptance
criterion.

## 17. A mock stands in for exactly the thing in doubt

This has now happened twice, and both times the mock was hiding the question the
test appeared to answer.

- **M1.** Every extraction test mocked the Anthropic client, so all of them
  would have passed identically if the vision path were completely broken. Four
  milestones stood on it. Closed by `tests/unit/live/extraction.live.test.ts`.
- **M3.** `lib/chat/stream.ts` called `after()` from inside an `AbortSignal`
  listener. `after()` reads Next's request context out of `AsyncLocalStorage`
  and throws without one, and that context does **not** propagate into an abort
  listener. So AC 12's partial persist threw inside an event listener and never
  ran. The test mocked `after` and asserted the mock had been called — which
  says nothing about whether the real function would work — and the mock ALSO
  invoked its callback immediately, which production never does. Two independent
  ways for the same test to pass over a dead code path.

The second half is the sharper lesson. A mock is not just a stand-in for
behaviour; it is a stand-in for **timing and preconditions**, and a mock whose
timing is more forgiving than production's invents a passing path that does not
exist.

**Rule:** when the question is whether an API is *callable at all* in a given
context — a request-scoped helper, a platform global, a vendor call — a mock
cannot answer it, and asserting the mock was called answers a different
question. Either exercise the real thing behind `RUN_LIVE_AI=1`, or verify the
precondition directly (fifteen lines of `AsyncLocalStorage` proved this one).
And make every mock match production's timing: if the real one defers, the mock
defers.

## 18. An ADR's claims about a vendor are hypotheses, not decisions

M3's two ADRs were written carefully, reviewed, and still asserted three things
about the outside world that turned out to be false. All three surfaced within
hours of the code being written:

- **ADR-0013 §3** said a partial turn "resumes streaming into the same row".
  It cannot: assistant prefill returns a **400** on Opus 5, so a truncated reply
  cannot be continued at all.
- **ADR-0013 §6** typed the client stream primitive as throwing on a non-2xx —
  which contradicted §2 of the same ADR, where the caller is told to treat an
  error event and a non-2xx identically.
- **Plan §4** accepted a lazy KaTeX chunk on the chat route as a necessary
  departure from ADR-0005, reasoning that a partial reply's LaTeX cannot be
  server-rendered. True, and irrelevant: the terminal `done` event already
  carries server-rendered HTML, so no KaTeX ships to the browser at all.

There is a clean line between the two kinds of statement in these documents. A
decision — "the problem text travels as a user message, never as a system
instruction" — is ours, and holds because we say so. A claim about what a vendor
or framework *does* is a hypothesis, and the document has no way to know it is
wrong.

**Rule:** when an ADR asserts vendor or framework behaviour that the design
depends on, mark it as an assumption and say what falsifies it. The implementer
who finds it false records a dated revision note in place — all three above are
now written into ADR-0013 — rather than silently building something else. A
divergence nobody wrote down becomes the next reader's confusion.

## 19. A declared cascade is invisible to the unit suite

Third occurrence, and the second *after* lesson 13 was written.

`onDelete: Cascade` is a line in `schema.prisma` that no unit test can reach,
because no unit test touches a foreign key. Every mocked test passes whether the
cascade fires or not. ADR-0017's checkpoint cascade was half-tested (M2.5's
review added the other half); M3's AC 16 — which plan §6.1 names explicitly —
had no test at all until M3's review. In both cases the cascade was correct.
Nothing had ever checked.

Lesson 13 covers an ADR that *describes* a control that does not exist. This is
narrower and more mechanical: the control does exist, in the schema, and the
test layer that would notice it missing is the one layer nobody remembers to
write.

**Rule:** every `onDelete: Cascade` that touches student data gets an
integration test naming it, and the test asserts a SET is empty — a count over
the child rows — rather than checking known ids one by one. A count is the only
form of the question a future column cannot slip past. This is now a checklist
item in `qa-tester`, not a habit.

## M4 — whiteboard lessons (2026-08-28)

M4 was built across nine slices, measured in a browser for the first time, then
reviewed. **Thirteen findings, four of them blockers.** The build itself was
sound — the `after()` bug from M3 was not repeated anywhere, refusal-over-
defaulting held, and every consent gate this project has historically broken was
correct and tested. What follows is only what recurred.

## 20. A fixture must be a state that some writer actually produces

**Fourth occurrence of lesson 17's family, and the sharpest form of it yet.**
Twice in M4 a test passed by describing a system that cannot exist:

- `author.test.ts` mocked the SDK's `parse` as *resolving* `{ parsed_output:
  null }`. The real `zodOutputFormat(...).parse` **throws** on a schema
  violation. So the mock created the only universe in which the `PARSE_FAILED`
  branch runs — and in production that branch was dead for the whole life of the
  code. Every malformed lesson was reported to a child as "a service we depend
  on is temporarily unavailable".
- `dto.test.ts` built a `FAILED` lesson whose **current** version carried a
  `failureCode`. No writer produces that row: `currentVersionId` is repointed
  only on success, so the current version is by definition the one that did not
  fail. The test proved a mapping that nothing could ever reach, while
  `failureMessage` was null in every state the code can actually reach.

Lesson 17 said a mock must not be more forgiving than production. This is the
same error one level up: it is not the mock's *timing* that was wrong, it is the
*state* being asserted. Both fixtures were internally coherent, well commented,
and impossible.

**Rule:** a fixture must be a state some writer in this codebase actually
produces, and the test says which writer, by name. "Which function writes this
row?" is the question. If it cannot be answered, the test is describing an
imaginary system and will stay green through any change to the real one.

## 21. Assert the output, not only the side effect

`reapIfStale`'s lost-race test asserted that `lessonScriptVersion.updateMany`
was **not called**. That was true, and it was the smaller half. It never looked
at the returned object — the entire output of the function, and the thing both
callers render — which was a hard-coded `FAILED`. So a lesson that finished
authoring moments before the reaping read was shown to a child as a failure
while a good `READY` script sat in the row, and a reload made it reappear.

The function's own docstring promised the opposite behaviour, and both sibling
implementations already did it correctly. A test that looked at the return value
would have caught it on the day it was written.

**Rule:** when a function returns a value its callers render, a test of that
function asserts the returned value. Asserting only what it wrote — or did not
write — checks the half that is easy to see.

## 22. A coverage test that walks its own registry cannot see an omission

`retention-policy-coverage.test.ts` asserted that every `RETENTION_POLICY` entry
with a window has a job step, and every job step a real entry. Airtight — for
the entries that exist. M4 added three Prisma models holding data derived from a
child's schoolwork, gave them no entry at all, and the suite stayed green. The
data was retained indefinitely, and `/retention` — the parent-facing COPPA
disclosure, rendered straight off that same array — said nothing about it. A
retention notice that omits a category is not incomplete, it is inaccurate.

The test iterated the registry it was checking. An omission from that registry
is invisible from inside it.

**Rule:** a coverage test iterates the **source**, not the registry — the Prisma
schema, the route directory, the filesystem — and fails on anything the registry
does not account for. It is now enforced: adding a model to `schema.prisma`
fails the suite until somebody classifies it as covered by a policy key or
explicitly outside it, with a reason. Falsified by mutation, not by reading.

## 23. A document may not claim a property the code does not have

Lesson 18 said an ADR's claims about a **vendor** are hypotheses. M4 produced
the same failure about our own code, which is less forgivable because it is
checkable.

ADR-0019 §4 stated that AC 15 (`prefers-reduced-motion`) is satisfied because
"animation is a CSS transition on the placement layer and a stroke reveal on the
overlay", and honouring the preference is removing them. **Neither effect was
ever built.** The only motion-related token in the components changed no value,
and there was no stroke reveal at all. The criterion was *vacuously* true — and
a `usePrefersReducedMotion` hook, a `reducedMotion` prop and a passing test that
asserted the class string was present and then absent made it look implemented.

Vacuous truth is the dangerous kind: a plainly unmet criterion gets built, while
this one was ticked off three times over.

**Rule:** before an ADR is Accepted, every "this buys us AC N" bullet is checked
against the code that implements it, and any bullet describing unbuilt work is
marked as intent rather than consequence. ADR-0019's claim is struck by a dated
revision note, the plumbing is deleted, and the M4 spec now records AC 15 as NOT
met with M5 owning it — because M5's narration is the first real timeline in the
product and the first thing that will actually need the preference.

## 24. Scope a review by file list, not by milestone

Not a lesson about an agent's judgement — a lesson about how they are
dispatched, and the most expensive mistake of this milestone.

The M4 review was first sent to one `code-reviewer` and one `security-reviewer`
across the whole milestone: 73 files, ~7,500 lines. The code reviewer spent its
entire 60-turn budget reading and **reported nothing at all** — 158k tokens, 71
tool calls, zero findings. Re-dispatched as four reviews with explicit file
lists, a named priority order, and "begin writing your report by turn 35 no
matter what", the same work produced thirteen findings including four blockers,
each reproduced with a throwaway probe rather than argued from reading.

The agents were not the constraint. The brief was.

**Rule:** a review is scoped by an explicit file list, split by concern, not by
"the milestone". Above roughly fifteen files, split it. Every brief carries a
reporting budget and an instruction to **name what it did not reach** — an
unreviewed area reported as silence is worse than one reported as unreviewed.

## What the pipeline got right in M4

- **The reviews found things no test could.** The dead arrowhead marker (every
  arrow drew as a bare curve, and the e2e check that counts `svg *` could not
  see it), the primary button that did nothing at the end of a lesson, and the
  authoring cap that a hundred parallel requests walk straight past. All three
  were reproduced empirically before being reported.
- **A reviewer wrote its finding to its own memory before it died.** The session
  that produced the retention gap was killed mid-run; the finding survived in
  `.claude/agent-memory/security-reviewer/` and was recovered and verified
  independently. Agent memory earned its place.
- **The M3 lesson held.** Every `after()` call site in M4 registers eagerly, in
  request context, closing over nothing but an id. The bug that defined M3 did
  not recur.

## Not acted on

- **A contract row that contradicts itself.** Plan §3.3's endpoint 39 says both
  "Idempotent" and "409 if already closed". Resolved by reading them as being

- **A distress turn consumes one of the session's twenty turns**, and two

### Added after M4 (2026-08-28)

- **The layout clamp bounds the border box while `overflow-hidden` clips the
  padding box**, leaving a 1px sliver of the defect it fixes. Real, tiny, and
  fixing it would couple the jsdom harness to four more layout properties.
  Recorded in `CLAUDE.md`.
- **`LessonFlag.versionId` and `Lesson.currentVersionId` have no foreign key.**
  The flags route resolves the body-supplied id inside the already-owned
  lesson, so there is no cross-student write today — but that route is the only
  thing preventing one, and the schema records no such intent. One occurrence.
- **Background authoring never re-checks consent** — a ~60s window in which a
  parent withdraws and a lesson is still written. Deliberately not fixed here
  because it is **not an M4 regression**: M1's confirm, M2's retry, M2.5's
  checkpoints and M3's turns all behave the same way. Fixing it in one milestone
  would leave three inconsistent. It needs a decision about what "withdrawal
  stops new data" means for work already in flight, taken once, across all four.
- **`LESSON_PROMPT_VERSION` is still `"m4.0-probe"`** and every lesson a child
  sees carries that stamp. Cosmetic until someone queries by it.
- **The prompt and the validator disagree about same-step ordering** — the
  prompt says an annotation may reference an element written in the same step,
  the validator rejects it if it appears before its target in that step's `ops`
  array. A model obeying the prompt literally produces a script we discard. One
  occurrence, and no measured instance of it happening.
